Developer Portfolio — Project Context
What this is

A single-page developer portfolio site for a junior fullstack developer (self-taught, ~1 year experience) job hunting in Finland. Goal: get recruiters to understand who I am, see real project work, and contact me — in under a few seconds of scanning.

The design originated in Claude Design (structural reference: dark editorial tone, bold oversized headline treatment) and was handed off here as a working prototype. Currently contains placeholder copy — real content (bio, project descriptions, links) will be swapped in incrementally. Do not treat placeholder text as final intent; ask before assuming what real copy should say.

Tech stack
Next.js (App Router) + TypeScript + Tailwind
Component structure/tokens came from the Claude Design handoff bundle — preserve existing component boundaries and design tokens rather than introducing new ad hoc styling patterns, unless a change is explicitly requested.
No shadcn/ui — components are the ones generated by Claude Design's own system.
No backend / no database. Static site, contact via mailto + external profile links (GitHub, LinkedIn), not a contact form.
Page structure (single page, anchor-nav)
Nav — name/logo, anchor links (About, Projects, Contact), Download CV button
Hero — name, one-line pitch, availability/location subline, CTAs
About — bio, tech stack split into "Core skills" / "Also exploring" tiers
Projects — exactly 3 cards: ToolShare, RAG Chatbot, LeaguePipeline. Each card: name, one-line problem statement, tech tags, screenshot, GitHub link (+ live demo if one exists)
Contact — prompt line, Gmail / GitHub / LinkedIn links, Download CV again
Footer — name/copyright

Keep this a single page. Do not split into multiple routes/pages unless explicitly asked (e.g. a future per-project deep-dive page is a possible v2, not now).

Build order / current priorities
✅ Static structure and layout first — no animations yet
⬜ Verify responsive behavior in real browser (not just Claude Design canvas) across mobile/tablet/desktop
⬜ Swap placeholder copy for real content once layout is confirmed solid
⬜ Add minimal animations only after static version is approved: candidates are fade-in-on-scroll per section, subtle hover lift on project cards, smooth-scroll for nav anchor links. Nothing flashier than that — avoid parallax or heavy page-transition effects, this is a junior dev portfolio, not a creative agency site.
⬜ Add real screenshots/GIFs to project cards (replacing placeholder image areas)
⬜ Push to a public GitHub repo with a proper README before treating this as "done" — the repo itself is part of the portfolio.
Working style / how to communicate with me
I'm self-taught (~1 year in), no formal CS background — explain why, not just what. I want to be able to defend technical decisions in interviews, so connect suggestions to underlying fundamentals/tradeoffs where relevant.
When something is broken or wrong, tell me directly — don't soften bad news or bury it in caveats.
When debugging, walk through the reasoning step by step rather than jumping straight to a fix.
I review code myself before accepting it — don't assume a suggestion is final just because it compiles/runs; flag tradeoffs so I can make the call.
OS: Windows with WSL (Ubuntu) — assume WSL-compatible commands/paths, not raw Windows paths or Windows-only tooling.
Things to avoid
Don't reintroduce multi-page routing for this v1.
Don't add a backend/contact form — mailto + profile links are the deliberate choice.
Don't overwrite placeholder content with invented copy — ask first, or clearly mark anything you draft as a suggestion.
Don't add animation/interaction libraries until the static version is confirmed and I've said to move to that step.

## Working style
- Work directly on `main`. When asked to make a change, edit the files and stop —
  do not run `git add`, `git commit`, `git push`, or `gh pr create` on your own.
- Leave changes uncommitted in the working tree until the user runs `/branch-and-pr`
  themselves to package and ship them.
Commit messages use Conventional Commits with a mandatory scope: `type(scope): description`. Types: feat, fix, docs, style, refactor, perf, test, chore, build, ci. Scope names the part of the codebase affected (e.g. `frontend`, `db`, `auth`, `messages`, `ci`). Add an optional body (blank line after the subject) when the change needs context — what and why, not how. Example: `fix(messages): scroll thread to newest message on load`.
